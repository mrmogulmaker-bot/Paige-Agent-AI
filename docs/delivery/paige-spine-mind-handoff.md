## What this slice does

PAIGE can state what a recorded Pipeline stage outcome proves for the active tenant and a
selected client, cite its safe reference, and say plainly when she does not know.

- Retrieval: `_shared/paige-spine/mindEvidence.ts` — the Pipeline domain's Mind projection.
  It reads through the merged safe adapter `public.get_pipeline_spine_evidence` and adds
  three things the raw signals do not carry: a citation, an explicit freshness word, and the
  read-only boundary.
- Chat: `_shared/paige-spine/chatEvidence.ts` now renders that projection instead of the raw
  signals, so Chat and Mind cannot give a person two accounts of the same record. Its
  exported names and signatures are unchanged, so `paige-ai-chat/index.ts` needed **no edit**
  — its call site, caller-scoped client, abort-backed scope check and buffered final-scope
  gate all behave exactly as before.
- Client scope: the Pipeline deal card points PAIGE at the deal's client through the existing
  `paige:open` event. `src/solo/paigeClientScope.ts` holds it; `SoloApp` listens; the Solo
  PAIGE fold reads it for the active account only.

## The Spine Change Request, and its exact bound

**Requested change.** The Chat-facing evidence block may name the opaque `rail:<uuid>` source
reference, and states the read-only boundary. Previously `chatEvidence.ts` withheld the
reference deliberately, and `paige-spine-chat-binding.test.ts` asserted its absence.

**Why it needed a request rather than an edit.** `docs/architecture/paige-spine-foundation.md`
names the Chat adapter contract as a shared primitive. Changing what crosses into model
context is a change to that contract, not a change inside one domain.

**Approved bound (owner, 2026-09-02).** The `rail:` reference is the approved safe citation
for this first slice. It must stay tenant-scoped, non-dereferenceable outside authorized
context, and reveal none of the forbidden raw fields. Nothing else was widened.

**Honest note on what the citation contains.** `source_record_ref` is `'rail:' || <the Rail
event id>`, so the Rail record's own UUID is inside it by construction. That is the ONE
identifier permitted to cross, it names a record rather than a person or a deal, and it
resolves only back through the same guarded lens. It is not a deal id, client id, contact
id, user id or tenant id — all of which remain forbidden. `paige-spine-chat-binding.test.ts`
now asserts the UUID appears exactly once and only inside the citation, never loose.

## The backend change this required, and why

The locked decision was to carry client context on the existing `paige:open` pathway. Two
facts made that unreachable as written, and both were found by reading current main:

1. **`paige:open` had no listener.** Three surfaces dispatched it; nothing consumed it. Every
   "Ask PAIGE" on Pipeline dispatched into nothing. `SoloApp` now listens.
2. **A Pipeline deal could name its client but not identify it.** `PipelineDeal` carried
   `clientName` only, so a deal card had no client scope to hand over.

`supabase/migrations/20261041000000_pipeline_deal_carries_its_client_reference.sql` re-creates
the innermost projection `get_pipeline_workspace_pre_identity` with **one added key**,
`client_id`, read from the ALREADY-JOINED and ALREADY-FILTERED `c` — never from
`d.contact_client_id`. Reading it off `c` means it is null in exactly the cases where the
client is not visible to that caller, so the identifier can never out-run the name beside it.
Every predicate is carried over verbatim; the file was generated by extraction rather than
retyped. No new grant, table, policy or authority.

### For `docs/brain/lessons-learned.md` — append

> ### A dispatched event with no listener is not a pathway
>
> **Symptom.** A locked technical decision named "the existing `paige:open` pathway" as the
> way to carry client context into PAIGE. Two Pipeline buttons and one Funding surface
> dispatched that event. Nothing anywhere listened for it.
>
> **Root cause.** `grep` for a dispatch proves a producer exists. It says nothing about a
> consumer, and a `CustomEvent` with no listener fails silently and successfully — there is no
> error, no console warning, and the button still animates. Both halves had been reviewed
> separately and each looked correct.
>
> **Rule.** When a seam is named as existing, verify BOTH ends before designing on it. For an
> event, grep the dispatch AND the `addEventListener`; a producer inventory (§37) that stops
> at producers is half an inventory. The same shape recurs with a registered check nobody
> scheduled (§68) and a migration nobody applied (§32.a): the artifact exists, the pathway
> does not.

## Known gaps, stated rather than smoothed over

- **The control opens PAIGE; it does not ask the question.** The deal card's button is labelled
  *"Open PAIGE for this client"* rather than *"Ask…"* because opening scoped is all it does. The
  event carries a `prompt`, matching the shape the two pre-existing dispatches already use, but
  no listener consumes one yet — prefilling the composer would mean editing `PaigeAIChat.tsx`,
  which PR #729 owns. The person types their question; PAIGE then answers from the record.
- **Setting a client scope resets the transcript.** That is the existing request fence doing its
  job — `scopeEpoch` is tenant plus client, so a client change invalidates the turn and clears
  the conversation. It is correct, and it is also the first thing a person will notice.
- **The in-context strip is built from the Solo shell's existing primitives** (`spw-truth`,
  `spw-link-button`) rather than a new treatment, and has **no rendered proof**. Its existence
  and its Clear control are correctness — a scope you cannot see or release is a scope you can
  ask the wrong question under. How it should look is Claude Design's, and is flagged for them.
