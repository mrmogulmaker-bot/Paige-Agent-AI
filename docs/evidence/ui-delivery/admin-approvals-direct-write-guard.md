# UI delivery evidence — delete unmounted approval surfaces + guard the live approve invariant + extend the orchestration DB guard to INSERT (#15)

This slice **removes** two UNMOUNTED approval surfaces (`src/pages/admin/ApprovalsInbox.tsx`,
`src/pages/admin/ApprovalDetail.tsx`), adds a CI guard, and — per the owner's 2026-09-13 decision —
**extends the orchestration direct-approve DB guard to the INSERT path**. External Codex review +
primary-source verification established that neither file is imported or routed anywhere in
production (App.tsx's only approvals route is `/app/approvals → ClientApprovals`); the MOUNTED
approve surfaces (`ApprovalRow` via `DraftsAwaitingPanel`/`GamePlanApprovals`, and the Solo/Agency
Command Center hooks) **already** route approve through the canonical `execute-approval` seam, so the
"no direct browser `status='approved'` write" invariant is already met in production. Owner decision
(2026-09-13): guard the live flow + delete the dead files, rather than harden unreachable code
(§70). There is **no visible interface change** — the deleted surfaces were unreachable and the
mounted surfaces are untouched.

**DB guard extension (owner-directed into #15, 2026-09-13).** The fix-forward guard
(migration 20270306000000) already refuses a JWT caller from TRANSITIONING a `source='paige_orchestration'`
row to approved (and proves the ledger terminal for the service-role executor path), but it was a
BEFORE UPDATE trigger, so an INSERT that created a `source='paige_orchestration'` row *already at*
approved slipped past it. Migration 20270317000000 makes the same guard `tg_op`-aware and re-creates
its trigger as BEFORE INSERT OR UPDATE: an authenticated caller can now neither CREATE an
already-approved orchestration record nor transition one to approved outside `execute-approval`.
**NARROW (§13):** this closes the orchestration INSERT+UPDATE approve path ONLY — it does NOT make the
database globally reject every direct approval write. A non-orchestration approval is untouched by the
guard on both paths; the broader table-wide approvals-RLS redesign (the §59 global-role trap) is the
separate, owner-decided next Orchestration security slice, deliberately not pulled in here.
