  1. Give this workspace a pipeline with stagesStage automations attach to a deal moving between stages. This workspace has no pipeline and no deals, so there is nothing to attach a rule to.

The minimum missing contract

Everything else this flow needs already ships. These four are what stand between a Solo owner and a working automation.

1
A step that actually executes the rule

The stage trigger fires, enforces consent and then POSTs to an external webhook. No code path takes a triggered event plus its rule and produces a draft or a send. This is the one gap that blocks everything: without it an automation can be authored and can fire, but can never do anything.

Already shipping and reusable: pre-send-pipeline (the five legal gates), channel-adapters (outbound send), paige_pending_approvals (the draft lane), railAutomation (telemetry). The missing piece is the function that drives those four.

2
A trigger that does not require a pipeline

A rule is keyed on pipeline_id and to_stage_id, so a workspace with no pipeline cannot author a single automation. Either give the workspace a pipeline, or admit a second trigger shape.

Already shipping: the rule table, its RLS, and the deal-stage trigger itself.

3
A dry-run that reports an outcome without sending

Nothing can currently answer “what would this do?”. The result shape already exists as PreSendOutcome; what is absent is a callable that evaluates the gates for a test contact and returns which one it lands on.

Already shipping: the gate order, the outcome enum, and consent and suppression reads.

4
One run history across both engines

Stage runs land in stage_automation_events, workflow runs in paige_workflow_runs. There is no single read, so “manage” cannot show a person one honest timeline.

Already shipping: both stores, both with real status vocabularies including honest skip reasons.
